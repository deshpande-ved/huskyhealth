# Epic: Apple Health parser

## Purpose

An athlete can hand HuskyHealth the export file Apple Health already makes (`export.zip`, or `export.xml` on a Mac) and get their last 60 days of training turned into the Features JSON the engine reads, on the phone, with no network and no install (DEC-2, DEC-3). This is the main way data gets in (feature F3). Without it, nothing downstream has real input.

---

## Scope

Spec: runbook Part E, epic E03 (sources: plan 6.1, 6.3, 6.5, held in the memory files listed below). Binding acceptance list:

- A hand-written `tests/fixtures/synthetic-export.xml` (self-closing and multi-line Records, a Workout with WorkoutStatistics, an old-style `totalEnergyBurned` Workout, route and ECG entries) parses to the expected features.
- `.zip` and `.xml` both work; the worker reports progress.
- Features contain day offsets only, and normalized source names.
- manual (Ved): his real export runs locally and prints counts; it is never committed (SAFE-1).

Plus the constraints from the sources and rules:

- Parsing streams the file (never loads it whole) in a Web Worker; only `export.xml` is decompressed from the zip.
- Only the six allowlisted record types are kept; routes, ECGs and clinical records are never opened (DEC-13, PRIV-3), shown by an explicit test.
- No network in the worker, `features.js` or anything they import (PRIV-1), shown by grep.
- Overlapping workouts from other apps are deduped, preferring the Watch (plan 6.1).
- Features JSON matches the 6.5 contract (`v`, `source`, `window_days`, `max_hr`, `days[]`, `workouts[]`), plus one per-workout boolean `hr_sample_ok` (at least one HR sample per 15 s), which gives E02S04's data gate its input (R-4c).

---

## Out of Scope

- Garmin: `.FIT` import and the Garmin parser (E09). Garmin data arriving through Apple Health sync is just Apple Health records here (DEC-4).
- The import UI, file picker and `app.js` wiring; IndexedDB storage (E04).
- Engine formulas themselves (E02); this epic calls them.
- The PWA shell and the service worker cache strategy (E01). E03S01 to E03S03 each add their own files to `SHELL` in `web/sw.js` (R-1).
- Committing any real export or anything derived from it.

---

## Stories

> Stories are tracked in the backlog. This list is descriptive only.

- E03S01: Read the records and workouts we need from export.xml text
- E03S02: Import a .zip or .xml file in the worker, with progress
- E03S03: Turn workouts into feature rows (sport, zones, effort, source, day)
- E03S04: Build the full Features JSON and prove it on the synthetic fixture
- E03S05: Run Ved's real export locally and print counts only

---

## Success Metrics

- `node --test` passes on the synthetic fixture for both `.xml` and an in-memory `.zip`.
- The fixture's route, ECG and clinical entries are proven unread; the PRIV-1 grep is empty.
- The Features JSON carries `hr_sample_ok` on each workout, and `web/sw.js` SHELL lists the worker, the fflate file and `features.js` (grep and `node --test`).
- manual (Ved): his real export prints plausible counts on the Mac; `git status` shows nothing new.

## Dependencies

- E01 (PWA shell): E01S03 (`web/sw.js`). E03S01, E03S02 and E03S03 each add their own file to `SHELL` (worker, fflate vendor file, `features.js`) and bump the cache name (R-1).
- E02 (Engine): E02S01 supplies the root `package.json` (`"type": "module"`, R-4d) that E03S01 runs under, and the `zoneMinutes`, `trimp` and `srpe` functions that E03S03 and E03S04 use. The scanner (E03S01, E03S02) needs no engine code.
