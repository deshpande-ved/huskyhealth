# Story: Collect on open

## User Story

**As an** athlete with convenience mode on,
**I want** HuskyHealth to pick up my new workouts by itself when I open it,
**so that** my readiness call is current without re-exporting Health, and the relay's copy is gone.

---

## Context

Plan 5.4, "Each sync" step 5. When the app opens and the mode is on: `GET /v1/drop/<box>` with the read secret → `openDrop()` (memory sketch: RSA-OAEP unwraps the AES key, AES-GCM decrypts) → turn the payload (schema from E06S04) into features with E03's `features.js` → merge the new days into the stored features JSON. The relay deletes the drop on read (E06S01), so the server copy is gone.

H-4 (unverified): Python `seal()` (OAEP SHA-256, MGF1 SHA-256) and WebCrypto RSA-OAEP with `hash: "SHA-256"` agree. This story's cross-language test decides it.

---

## Acceptance Criteria

- [ ] AC1: the cross-language round trip passes: a `node --test` test makes a WebCrypto key pair, runs the relay's Python `seal()` on a synthetic payload (via `python3` subprocess), and `openDrop()` returns the same JSON. If it fails because the OAEP hash or MGF1 parameters disagree, STOP and report; don't change the padding on one side to make it pass.
- [ ] AC2 (compliance): on app open with the mode on, the app makes exactly one `GET /v1/drop/<box>` with the read secret, decrypts and merges; with the mode off it makes no call. The new entries `/js/sync-collect.js` and `/js/sync-merge.js` are added to `SHELL` in `web/sw.js` as root paths (never `web/js/...`), and `CACHE` is bumped (R-1). Checked by `node --test` with a stubbed `fetch` and a grep on `web/sw.js`.
- [ ] AC3: merge adds the new days and workouts to the features JSON, places them by day offset using the drop's `age_s`, replaces a day that already exists rather than duplicating it, and merging the same payload twice changes nothing. `ref_day` (the local day number the offsets count from) lives in the `sync` store, never in features; before each merge the stored `days[]` shift by today − `ref_day` and are trimmed to `window_days`. The features store holds no calendar dates. Checked by `node --test` on synthetic fixtures, including a test of the shift.
- [ ] AC4 (compliance, PRIV-2): after a merge IndexedDB holds only the features JSON shape (no raw heart-rate samples, timestamps, device or source names); a `node --test` test asserts the stored object's keys match the features contract.
- [ ] AC5 (error-handling): a 404 (no drop), a network error, a decrypt failure or a payload that fails the schema leaves features unchanged, keeps the mode on, shows at most one plain status line, and logs nothing about the content. Checked by `node --test`.
- [ ] AC6: manual (Ved): with a drop posted by `curl` from the Mac (synthetic payload), opening the installed PWA shows the new workout, and a second `curl` GET with the read secret returns 404.

## Out of Scope

- The drop box itself (E06S01), pairing (E06S02), the Shortcut (E06S04), turn-off (E06S05).
- Any change to engine formulas; merged data goes through the same `features.js` and engine as an import.

---

## Dependencies

- E06S01 (GET drop, `age_s`), E06S02 (keys, read secret in IndexedDB), E06S04 (payload schema). Cross-epic: E03S04 (`features.js`, full Features JSON contract), E04S06 (`db.js` features store, app shell).

---

## Notes

- The round-trip test needs `python3` with `cryptography` (added to `relay/requirements.txt` by E06S01); skip with a clear message if `python3` isn't found, but CI/Delivery must run it at least once and record the result.
- `ref_day` is the local day number the features' day offsets count from. It lives in the `sync` store beside the keys (it never leaves the phone), never in the features JSON.
- Collect runs once per app open and never on a timer.
