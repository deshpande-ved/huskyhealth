# Story: Main screen figures from fixture features

## User Story

**As an** athlete,
**I want** to see today's call, my HRV band, 60 days of load and my fitness and fatigue on one screen,
**so that** I know whether today should be hard or easy and why.

---

## Context

This story puts the engine's output on the main screen as four ASCII figures: the call banner (`HARD` / `EASY` / `NO DATA`), the HRV band gauge, the 60-day training calendar and the fitness/fatigue plot. It works from a synthetic fixture features file (the 6.5 contract), so it does not wait for the Apple parser. Each figure is a `<pre role="img">` with an `aria-label` carrying the real numbers (FE-4), and each figure and number links to its References card (FE-2). Building the figures as plain data first (text, label, card id) and painting them second keeps the work testable in Node.

---

## Acceptance Criteria

- [ ] AC1: From `tests/fixtures/features-60d.json` (synthetic, 60 days, enough HRV for a call), the screen model produces exactly four figures (banner, gauge, calendar, plot), and the banner shows the engine's call for that fixture. Checked by `node --test tests/view.test.js`.
- [ ] AC2: Each figure has a non-empty `aria-label` with the real, rounded numbers, e.g. "Fitness 62, fatigue 71, form −9" for the plot; the gauge label gives the 7-day HRV position in SD and the reading counts; the calendar label gives the 60-day total and the highest day. Checked by `node --test tests/view.test.js` against numbers computed from the fixture by the engine.
- [ ] AC3: Each figure carries a source line (its last row) built from the engine's `source` for it (method and version), and each figure and each number shown next to it links to `#ref-<id>`. Every such id exists in `web/index.html` (from E04S03), and every engine source id in `SOURCES` maps to an existing card through a map in `view.js` (for example `readiness` to `ref-readiness`). Checked by `node --test tests/view.test.js`.
- [ ] AC4: Every line of every figure is 44 columns or fewer. With empty features or too little HRV, the banner reads `NO DATA` and its label says how many HRV days are present and needed (3 of the last 7, 14 baseline). Checked by `node --test tests/view.test.js`.
- [ ] AC5 (compliance, FE-1 / FE-4): figures are painted into `<pre role="img" aria-label="…">` with `paint()` / `textContent`; colors come from the E04S02 classes. FE-1 greps from `frontend.rules.md` return nothing over `web/`.
- [ ] AC6: Any new JS module this story adds is listed in `web/sw.js` SHELL and `CACHE` is bumped, so the screen still loads offline. Checked by `grep` of the new path in `web/sw.js`.

> All acceptance criteria must be verifiable. Vague criteria are invalid.

## Notes

- STOP condition: if E02's engine does not return the readiness `z`, `n7` and `nBase` and the fitness/fatigue series as in the engine memory sketch, stop and report; do not recompute engine values in the UI (rules decide, CLAIM-3).
- Calendar input: daily load = `days[].trimp`; dominant zone per day = the zone with the most minutes across that day's workouts, `0` for rest days.
- The fixture is synthetic (SAFE-1): day offsets only, no dates, names or device names; source label "Apple Watch".
- Training language only (CLAIM-1): "hard is fine" / "easy", never "injury risk".
