# Story: Fitness/fatigue and monotony

## User Story

**As an** athlete,
**I want** my fitness, fatigue and form, my training monotony and my other day-by-day trends worked out from my daily load,
**so that** I can see how my training is building up over weeks, not just one session at a time.

---

## Context

Second engine story. It adds the multi-day rows of the 7.1 table to `web/js/engine.js`:
- fitness / fatigue / form: Banister et al. 1975, 42-day and 7-day impulse-response on daily TRIMP, seeded with the week-1 mean (7.2 sketch);
- monotony: Foster 1998, mean ÷ SD of the last 7 daily loads, flag > 2;
- the three other multi-day 7.1 rows, so every row has a hand-worked test somewhere in E02: load spike (Gabbett, disputed, info only), VO2 max trend (descriptive), sport-specific view (ours).

Known gap in the 7.2 sketch: with 7 identical non-zero loads the SD is 0 and `monotony` returns `null`, so the 7.4 scenario "7 identical loads, no rest → monotony flag" would fail. Mean ÷ 0 is unbounded, which is above 2, so it must flag.

---

## Acceptance Criteria

- [ ] AC1: `fitnessFatigue(dailyLoad)` matches a hand-worked example: loads `[10,10,10,10,10,10,10,80]` → fitness 11.667, fatigue 20, form −8.333 (to 3 decimals), and `series` has one entry per day. Checked by `node --test "tests/**/*.test.{js,mjs}"`.
- [ ] AC2: `monotony(last7)` returns `{ value, flag }` (state consumers read `monotony.flag`; `value` is `null` for identical loads): `[100,0,100,0,100,0,100]` → value ≈ 1.155 (population SD), flag false; 7 identical loads of 50 → value `null`, flag true; 7 zeros → value `null`, flag false; any value > 2 → flag true. Checked by `node --test "tests/**/*.test.{js,mjs}"`.
- [ ] AC3: `loadSpike(dailyLoad)` = sum of last 7 days ÷ (sum of last 28 days ÷ 4): 21 days of 100 then 7 days of 200 → 1.6; fewer than 28 days → `null`. It returns `flag: true` when the ratio is above 1.5 (Gabbett 2016 upper band, Ved decision R-4b), marked info only and worded as training load. Checked by `node --test "tests/**/*.test.{js,mjs}"`.
- [ ] AC4: `vo2Trend(days)` = least-squares slope of non-null `vo2` against day × 28: points (day −28, 45.0) and (day 0, 47.0) → 2.0; fewer than 2 points → `null`. Checked by `node --test "tests/**/*.test.{js,mjs}"`.
- [ ] AC5: `sportView(workouts, sport)` compares the latest session of that sport with the earlier ones (count, mean, sample SD, z of the latest TRIMP): earlier squash TRIMP `[100,120,140]`, latest 160 → mean 120, SD 20, z 2; fewer than 2 earlier sessions → z `null`. No multipliers. Checked by `node --test "tests/**/*.test.{js,mjs}"`.
- [ ] AC6 (compliance, FE-2 / CLAIM-1 / PRIV-1): every result of AC1–AC5 carries `source` from `SOURCES` (`fitness-fatigue`, `monotony`, `load-spike` with status `disputed`, `vo2-trend` with `descriptive`, `sport-view` with `ours`);  the `load-spike` citation reads "Gabbett 2016, Br J Sports Med" (no title); no string in `engine.js` says "injury"; `tests/engine/purity.test.mjs` still passes; `CACHE` in `web/sw.js` is bumped, checked by `node --test tests/web-sw.test.js`. Checked by `node --test "tests/**/*.test.{js,mjs}"` and `grep -ni "injury" web/js/engine.js` returning nothing.

## Notes

- Banister constants are the standard 42 and 7 days; don't tune them.
- Load spike: the 1.5 cut-off is Gabbett 2016's upper band, fixed by Ved's decision R-4b. It is the one threshold here that the 7.1 table doesn't state. Change it only by a new decision, not in this story.
- Daily loads for these functions are daily TRIMP from `dailySeries(features, "trimp", 0)` (a day with no workout is a rest day, load 0).
- Monotony uses the population SD, as in the 7.2 sketch.
