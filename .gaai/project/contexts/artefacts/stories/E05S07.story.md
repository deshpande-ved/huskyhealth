# Story: Build the BriefIn on the phone, with load flags

## User Story

**As an** athlete,
**I want** the app to turn my local results into the short, fixed list of numbers the brief needs, with my load alerts included,
**so that** the brief can mention repetitive training or a load spike while my workouts and dates stay on my phone.

---

## Context

`web/js/brief.js` exports a pure `buildBriefIn(features, result)` that maps the features JSON (6.5) and the engine's result (7.1/7.2) to the exact `BriefIn` shape the relay accepts. F9: the `monotony` flag (Foster, monotony > 2) and the `load_spike` flag ride along. It runs in the browser with no network (PRIV-1/2). The JSON/pydantic contract is pinned by a shared fixture.

---

## Acceptance Criteria

- [ ] AC1: Given the synthetic features + engine-result fixture, when `buildBriefIn` runs, then its output deep-equals `tests/fixtures/briefin-sample.json` (from E05S01), and `pytest tests/relay/test_schema.py` validates that same file with `BriefIn`. `buildBriefIn` applies the 8.3 rounding table, so the fixture is already pre-rounded: a pytest in that file asserts `bucketize(sample)` equals the sample without `v` (idempotent). Checked by `node --test tests/brief.test.js` and pytest.
- [ ] AC2: F9 flags: given engine results with monotony > 2 and/or the engine's load-spike flag set, then `flags` contains `monotony` and/or `load_spike` (in that order); with neither, `flags` is `[]`. Uses E02S02's load-spike flag (7-day load ÷ (28-day load ÷ 4) > 1.5), never a threshold set here. Checked by node --test (four cases).
- [ ] AC3 [compliance]: The output has exactly the `BriefIn` keys and `v: 1`; its only strings are the call, flag names and `Sport` keys; `JSON.stringify(output)` matches no date (`\d{4}-\d{2}`), no `source` or device label, and no per-workout array. Checked by node --test.
- [ ] AC4 [error-handling]: Integers where the schema wants integers (`hrv_days7`, `rhr_delta`, each zone %, each sport %), `null` where the engine has no value (e.g. `call: "not_enough_data"` gives `hrv_z: null`), and `zone_pct7` is `[0,0,0,0,0]` when there are no workouts. `rhr_delta` is the mean RHR of days -6..0 minus the mean of days -34..-7, rounded to an integer, and `null` if either window has fewer than 3 readings. If any value falls outside the schema range, `buildBriefIn` returns `null` so nothing is sent. Checked by node --test, with one `rhr_delta` case covering the two windows and the 3-reading null.
- [ ] AC5 [compliance]: PRIV-1: `brief.js` is pure: the PRIV-1 grep (`fetch\(|XMLHttpRequest|WebSocket|EventSource|sendBeacon`) and `grep -n "document\|window" web/js/brief.js` return nothing.
- [ ] AC6 (offline shell): `/js/brief.js` is added to the `SHELL` array in `web/sw.js`, the `CACHE` name is bumped to the next version, and the expected SHELL list in `tests/web-sw.test.js` (E01S03) is extended to match. Checked by `node --test tests/web-sw.test.js` and `grep -n "/js/brief.js" web/sw.js`.

## Notes

Field sources (Discovery's mapping; confirm against E02's exported names):

| BriefIn field | From |
|---|---|
| `call`, `hrv_z`, `hrv_days7` | engine `readiness()`: `call`, `z`, `n7` |
| `fitness`, `fatigue`, `form` | engine `fitnessFatigue()` (last values) |
| `load7`, `load_prev7`, `srpe7` | sum of daily `trimp` for days -6..0 and -13..-7; sum of daily `srpe` -6..0 (`null` if none) |
| `monotony`, `flags` | engine `monotony()` and engine flags |
| `ramp` | the load-spike ratio, last 7 days ÷ (last 28 days ÷ 4) (7.1 "Load spike") |
| `zone_pct7`, `zone_pct42` | share of workout zone minutes in the last 7 / 42 days, rounded %; `zone_pct7` is `[0,0,0,0,0]` with no workouts |
| `vo2_trend_4w` | engine VO2 max trend (slope × 28 days) |
| `rhr_delta` | mean RHR days -6..0 minus mean days -34..-7, rounded; `null` if fewer than 3 readings in either window (AC4) |
| `sport_mix` | share of workout minutes by sport in the last 42 days, rounded % |

- STOP: if E02 does not expose a load-spike flag, or exposes `ramp`/VO2 trend under a different meaning, stop and report; do not invent a formula. The 1.5 cut-off is the agreed value (Gabbett 2016 upper band, E02S02), so a missing threshold is not a stop condition here.
- The 28-day figure in `ramp` and the load-spike flag is the weekly mean of the last 28 days (28-day sum ÷ 4), the same ratio as E02S02 AC3.
- Training language only in any comment or label (CLAIM-1): "load alert".
