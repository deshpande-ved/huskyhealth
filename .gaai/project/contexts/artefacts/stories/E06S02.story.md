# Story: Pairing in the PWA

## User Story

**As an** athlete,
**I want** to turn on convenience mode only after reading exactly what it sends, and get a pairing code for my Shortcut,
**so that** auto-sync happens only because I chose it, with a key that never leaves my phone.

---

## Context

Plan 5.4, "Off by default" and "Turning it on". Settings gets a **Convenience mode** toggle, OFF by default. Turning it on opens a consent screen. On confirm, `makeKeys()` (memory sketch) creates an RSA-OAEP 2048 / SHA-256 key pair with a non-extractable private key; the key pair, box ID and read secret go into IndexedDB; the public key goes to `POST /v1/box`; the app shows the pairing code (box ID + write secret) once, for pasting into the **HuskyHealth Sync** Shortcut.

Consent text must state, in the 5.4 wording:
- what is sent: new workouts since the last sync with their heart rate, plus the last 3 days of resting HR, HRV and effort
- who can read it: the Pi, in memory, for milliseconds
- how long it's kept: until the phone collects it, at most 24 h, memory only
- how to turn it off

---

## Acceptance Criteria

- [ ] AC1 (compliance, PRIV-4): with the toggle off (first run, and after cancelling the consent screen) there are no keys in IndexedDB and no network calls: a `node --test` test with a stubbed `fetch` and an in-memory IndexedDB asserts zero `fetch` calls and an empty sync store, and the `settings` store default (E05S08) has convenience mode `false`; the flag needs no store of its own and no DB version bump.
- [ ] AC2 (compliance): the consent screen shows the four points above in the 5.4 wording, says "de-identified" never "anonymous" (CLAIM-2) and makes no medical claim (CLAIM-1); Cancel leaves the toggle OFF. Checked by `node --test` on the rendered text plus the CLAIM-1/CLAIM-2 greps over `web/`.
- [ ] AC3: `makeKeys()` makes an RSA-OAEP 2048 / SHA-256 key pair whose private key is non-extractable: a `node --test` test asserts `crypto.subtle.exportKey("pkcs8", privateKey)` rejects and `privateKey.extractable === false`.
- [ ] AC4 (error-handling): on confirm, the app sends one `POST /v1/box` with only `{"pub": <base64 SPKI>}` to the relay origin, stores the key pair, box ID and read secret in IndexedDB, and never stores the write secret; if the call fails, the keys are discarded, the toggle returns to OFF and a plain status line says so. Checked by `node --test` with a stubbed `fetch`.
- [ ] AC5: the pairing code (box ID + write secret) is shown once with a copy button and is gone when the user leaves the screen; reopening Settings never shows it again. The UI uses no `innerHTML` and no inline CSS/JS (FE-1 greps return nothing). The new entries `/js/box.js` and `/js/sync-settings.js` are added to `SHELL` in `web/sw.js` as root paths (never `web/js/...`), and `CACHE` is bumped (R-1). Checked by `node --test`, the FE-1 greps and a grep on `web/sw.js`.
- [ ] AC6: manual (Ved): H-6 check. Pair on the installed iPhone PWA, force-quit, restart the phone, reopen: the private key is still in IndexedDB and still decrypts (a dev-only button or console check). If the key doesn't survive on iOS Safari, STOP and report; don't work around it (for example by making the key extractable).

## Notes

- E04's acceptance says "IndexedDB stores features only". The key pair, box ID and read secret are an explicit 5.4 exception that exists only while the mode is on; keep them in a separate `sync` object store so the features store stays features-only.
- No new runtime dependency. A dev-only IndexedDB shim for `node --test` is fine, or inject the store.
- WebCrypto `generateKey` with `extractable: false` still allows `exportKey("spki", publicKey)`, since public keys are always extractable.
