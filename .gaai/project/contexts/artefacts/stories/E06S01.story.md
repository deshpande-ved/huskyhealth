# Story: Drop box API

## User Story

**As an** athlete who turned on convenience mode,
**I want** the relay to hold my new workouts only as ciphertext that only my phone can open,
**so that** my Shortcut can hand off data while the Pi never keeps anything it can read.

---

## Context

Plan 5.4, steps "Each sync" 3–5 and "Limits". The relay (built in E05) gains four routes. `seal()` from the memory sketch encrypts each drop with AES-256-GCM and wraps the AES key with the box's RSA-OAEP public key (OAEP SHA-256, MGF1 SHA-256). Everything lives in a module-level `BOXES` dict in RAM; gunicorn runs one worker (PRIV-7), so a restart wipes it.

Routes (from `project/infra-relay.md`):

| Method | Path | Auth | Returns |
|---|---|---|---|
| POST | `/v1/box` | none, rate-limited | `{box, write, read}` |
| POST | `/v1/drop/<box>` | write secret | 204 |
| GET | `/v1/drop/<box>` | read secret | `{key, nonce, ct, age_s}`, then deleted |
| DELETE | `/v1/box/<box>` | read secret | 204 |

Secrets travel as `Authorization: Bearer <secret>`. `age_s` (whole seconds since the drop arrived) lets the phone place relative times without the payload carrying calendar dates (see E06S04).

---

## Acceptance Criteria

- [ ] AC1: `POST /v1/box` with `{"pub": <base64 SPKI>}` returns `{box, write, read}`, each from `secrets.token_urlsafe(16)` or longer; a key that isn't a valid RSA public key of at least 2048 bits → 422 with a generic message; the route uses E05S02's in-RAM global rate limiter at 30/min (over-limit → 429). The key check uses `cryptography`, which this story adds and pins in `relay/requirements.txt` (R-4h). Checked by pytest and `grep -n cryptography relay/requirements.txt`.
- [ ] AC2 (compliance): after a drop is posted, `BOXES` holds only the `seal()` output (`key`, `nonce`, `ct`) and metadata; a pytest posts a body containing a unique marker and asserts that neither the marker bytes, the base64 of the marker at all 3 alignment offsets, nor the base64 of the full body appears anywhere in `repr(BOXES)`.
- [ ] AC3: `GET /v1/drop/<box>` with the read secret returns the ciphertext once and deletes it (a second GET → 404); a drop older than 24 h is purged and returns 404 (pytest with a patched clock).
- [ ] AC4 (error-handling): a wrong or missing secret → 403 on POST drop, GET drop and DELETE box (compared with `hmac.compare_digest`); a body over 64 KB → 413 (a per-route cap, not the global `MAX_CONTENT_LENGTH`, because `/v1/listen` takes up to 200 KB); a second drop while one is pending → 409; an unknown box → 404. Checked by pytest.
- [ ] AC5: `DELETE /v1/box/<box>` with the read secret → 204 and the box is forgotten (later calls → 404). Checked by pytest.
- [ ] AC6 (compliance, PRIV-6): nothing is logged by the drop box: the PRIV-6 grep (`grep -rnE "log(ger)?\.\w+\(.*(body|request\.json|brief|prompt|audio|errors\(\))" relay/`) returns nothing, there is no `print` in `relay/dropbox.py`, and a pytest using `caplog` shows zero log records across a full create → drop → read → delete run. Error responses never echo input.

## Notes

- Plaintext lives only inside the request handler: read the body, call `seal()`, drop the reference. Never assign it to module state.
- Use `seal()` exactly as in the memory sketch (OAEP with SHA-256 and MGF1 SHA-256). E06S03's cross-language test checks it against WebCrypto (H-4).
- No Presidio on this path: the drop goes back to the phone only, never to a provider.
- An unbounded number of boxes could grow RAM; the AC1 rate limit is the only guard the spec asks for. Note any further cap as a follow-up, don't add one silently.
