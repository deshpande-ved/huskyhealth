# Story: Turn .fit files into features, with sports mapped

## User Story

**As a** Garmin owner,
**I want** my `.fit` activity files turned into the same training features as an Apple Health export,
**so that** I get load, fitness and fatigue without an iPhone Health export, and nothing about my routes or device is kept.

---

## Context

Plan 6.4 sketches `parse-fit.worker.js`: decode each file with the vendored SDK, take heart-rate samples from record messages and workouts from session messages, then call the shared `toFeatures()` (E03) with `source: "garmin_fit"`. This story puts that logic in a pure, DOM-free module (`web/js/fit-features.js`) so it runs under `node --test` and in the worker (E09S03). The worker itself is E09S03.

Garmin activity files have HR and sessions but no overnight HRV, so `ln_hrv` stays empty and readiness shows "not enough data" (plan 6.2). FIT files carry GPS positions and device details; PRIV-3 says collect less, so only an explicit field allowlist is read.

Sport mapping: our sports are `squash`, `running`, `other` (Features contract, plan 6.5). Plan 6.2 says "check how sample files label squash". Read the sport and sub-sport enums in the vendored SDK's profile; never guess values.

---

## Acceptance Criteria

- [ ] AC1: `fitToFeatures(buffers, { days, now })` returns a Features JSON matching the 6.5 contract (`v`, `source: "garmin_fit"`, `window_days`, `max_hr`, `days[]`, `workouts[]`), with day offsets only (no dates) and workout `source: "Garmin"`. Checked by: `node --test tests/fit-features.test.js` on synthetic FIT bytes built in memory by `tests/fixtures/fit-synthetic.js` (two sessions with HR records), comparing to hand-worked expected features, with a fixed injected `now` (as in E03S04) and run under both `TZ=UTC` and `TZ=America/New_York`.
- [ ] AC2: Sports are mapped from the SDK's sport/sub-sport values: running → `running`; squash (whatever value the vendored profile uses for it) → `squash`; any other value, a missing sport, or an unknown number → `other`. Checked by: a table-driven test in `tests/fit-features.test.js`. If the vendored profile has no squash value, map only running, say so in the PR, and do not invent one.
- [ ] AC3 (compliance, PRIV-3/DEC-13): Only allowlisted fields are copied out of the decoded messages: records `timestamp`, `heartRate`; sessions `sport`, `subSport`, `startTime`, `totalTimerTime`, `totalCalories`. The allowlist is a named constant in code. Checked by: the synthetic fixture includes GPS positions and a device/product name, and the test asserts `JSON.stringify(features)` contains none of them.
- [ ] AC4 (error-handling): A non-FIT buffer or a corrupt FIT buffer is skipped without throwing, and the result reports how many files were skipped (count only, no file names). With no valid files, the result is an empty-but-valid Features JSON. Checked by: `node --test`.
- [ ] AC5: Garmin-only features have `ln_hrv: null` on every day and `trimp > 0` on some day. Checked by: `node --test` assertion on the fixture output.
- [ ] AC6 (compliance, PRIV-1/SAFE-1): No network in the new module. Checked by: `grep -nE "fetch\(|XMLHttpRequest|WebSocket|EventSource|sendBeacon|import\(['\"]https?:" web/js/fit-features.js` returns nothing, and `git ls-files '*.fit'` prints nothing.

> All acceptance criteria must be verifiable. Vague criteria are invalid.

## Out of Scope

- Effort/RPE from FIT files; Garmin workouts have `effort: null` and `srpe: null`.
- Reading HRV, sleep or any message type other than record and session.

## Notes

- Never commit a `.fit` file: the pre-commit gate blocks `*.fit` (SAFE-1). The fixture is a JS module that builds bytes at test time.
- If `toFeatures()` from E03 cannot accept FIT workouts without a larger change than the 10-line hook above, stop and report rather than reshaping `features.js`.
- FIT timestamps come back as JS `Date` objects (plan 6.4); convert to day offsets inside `toFeatures()` as the Apple path does.
